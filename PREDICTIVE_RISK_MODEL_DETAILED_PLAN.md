# VaidyaSetu Predictive Risk Model - Full Technical Explanation

This document explains the complete predictive risk system used in VaidyaSetu, including:

- Which regression/modeling algorithms are used

## 2) What "Model" We Use in Production

VaidyaSetu uses a **Hybrid Predictive Engine**:

1. **Deterministic Clinical Rule Engine** (primary safety anchor)
   - Implemented in `backend/src/utils/riskScorer.js`
   - Computes baseline and questionnaire-informed scores for each disease
   - Uses explainable factor contributions (age, BMI, symptoms, family history, lifestyle, etc.)

2. **AI Adjustment Layer** (contextual refinement)
   - Implemented in `backend/src/services/predictiveRiskAiService.js`
   - Uses Groq model `llama-3.3-70b-versatile` for factor narrative + contextual final adjustment
   - AI is constrained by strict rules so it cannot rewrite deterministic anchors

3. **Deterministic Vitals + Mitigation Adjustments** (post-AI safety correction)
   - Additional disease-specific risk changes applied for abnormal vitals
   - Completed mitigation actions reduce risk with capped reductions

This gives:
- clinical explainability
- robustness if AI fails
- continuous updates as user data changes

## 3) Which Regression / ML Algorithms Are Used

For benchmark and accuracy evaluation, the project includes a full ML pipeline:

File: `backend/src/tests/predictive_accuracy_pipeline.py`

### Models included

1. **Logistic Regression** (core regression model)
   - `LogisticRegression(max_iter=1200, class_weight="balanced")`
   - Wrapped with `StandardScaler`
   - Best for interpretable probabilistic output

2. **Random Forest Classifier**
   - `RandomForestClassifier(n_estimators=500, class_weight="balanced")`
   - Captures non-linear relationships and interactions

3. **Histogram Gradient Boosting**
   - `HistGradientBoostingClassifier(max_iter=500, learning_rate=0.03, max_depth=4)`
   - Fast and strong on tabular health features

4. **XGBoost Classifier** (optional if installed)
   - `XGBClassifier(... objective="binary:logistic", eval_metric="auc")`
   - High-performance boosting baseline

### Dataset used for evaluation

- Public labeled benchmark: **Pima Indians Diabetes dataset**
- Features include glucose, blood pressure, insulin, BMI, age, etc.
- Pipeline performs zero-imputation fixes for clinically invalid zero values in key columns

## 4) End-to-End Risk Calculation Flow (Production)

### Step A - Data collection from Mongo

Per user (`clerkId`), system loads:
- onboarding profile
- active medications
- recent vitals
- questionnaire disease insights
- mitigation completion statuses

### Step B - Deterministic anchors per disease

For each disease in hybrid list:
- `baselineScore` from onboarding snapshot
- `questionnaireScore` from updated profile + questionnaire context
- factor list, protective factors, missing data factors, data completeness

These are generated by:
- `calculateDetailedInsights()` in `riskScorer.js`

### Step C - AI contextual adjustment (if available)

AI receives:
- baseline + questionnaire anchors
- top factors
- latest vitals
- meds + allergies
- prevalence evidence

AI is forced to obey:
- baselineScore and questionnaireScore must match deterministic anchors
- finalScore must start from questionnaireScore and adjust contextually
- output strict JSON schema

### Step D - Validation gate

If AI output is malformed or invalid:
- fallback to deterministic output automatically
- no user-facing crash

### Step E - Deterministic post-processing

1. Apply disease-specific **vitals adjustments** (e.g., BP, glucose, SpO2, heart rate, sleep, steps, hydration)
2. Apply **mitigation reduction**:
   - `reduction = min(15, completedSteps * 3)`
3. Clamp final score:
   - valid range: `2` to `95`
   - `-1` reserved for N/A diseases (example: male + PCOS)

### Step F - Final output object per disease

- riskScore
- riskCategory
- baselineScore
- questionnaireScore
- assessmentDelta
- factorBreakdown
- protectiveFactors
- missingDataFactors
- mitigationSteps
- precautions
- verification metadata

## 5) Mathematical Logic and Calculation Rules

## 5.1 Score Category Mapping

- `-1` -> `N/A`
- `<5` -> `Very Low`
- `5-25` -> `Low`
- `26-50` -> `Moderate`
- `51-75` -> `High`
- `>75` -> `Very High`

## 5.2 General Formula

For each disease:

`Final Risk Score = clamp( Base/Questionnaire Score + Vitals Delta - Mitigation Reduction )`

Where:
- **Base/Questionnaire Score** = deterministic disease logic output
- **Vitals Delta** = weighted additive risk from current abnormal vitals
- **Mitigation Reduction** = capped deduction from completed interventions

## 5.3 Diabetes example (IDRS-based)

Core factors in rule engine:
- age points
- waist circumference points
- activity points
- family history points
- symptom enrichments (thirst, urination, blurred vision, slow healing, tingling)
- medication/allergy impacts

Then vitals adjustment may further increase score if blood glucose status is borderline/high/critical.

## 5.4 Thyroid example (Likelihood-ratio style)

Uses prior prevalence probability:
- convert probability to odds
- multiply odds by symptom likelihood multipliers (fatigue, cold intolerance, dry skin/hair loss)
- convert odds back to probability
- apply medication protective effect if thyroid medication is active

## 5.5 Hypertension example

Weighted contributors include:
- age bands
- BMI class
- salt intake
- family history
- stress
- smoking/alcohol
- prior BP category / direct BP reading

Then vitals module adds extra delta for latest BP severity and related diseases.

## 6) Vitals Impact Matrix (Deterministic)

Current vitals logic adjusts disease risk based on status severity:

- **Blood pressure** -> hypertension, stroke, heart disease, CKD
- **Blood glucose** -> diabetes, pre-diabetes, fatty liver
- **SpO2** -> COPD, asthma, heart disease
- **Heart rate** -> heart disease, hypertension, anxiety
- **Body temperature** -> asthma, COPD (acute illness proxy)
- **Sleep duration** -> depression, anxiety, diabetes, hypertension
- **Steps** -> obesity, diabetes, pre-diabetes
- **Water intake** -> CKD, kidney stones

Each adjustment writes explainable factor objects:
- factor name
- display value
- numeric impact
- explanation
- category and source

So users can see exactly why risk changed.

---

## 7) Mitigation Completion Impact

Risk decreases only when mitigation completion is persisted in DB:

- source model: `MitigationCompletion`
- formula: `reduction = min(15, stepsCompleted * 3)`
- applied after deterministic/AI scoring

This prevents false score drops from temporary UI state.

## 8) Why This Architecture Is Defensible

### Clinical safety
- Deterministic anchors prevent uncontrolled AI drift.
- AI cannot change baseline/questionnaire anchors.

### Explainability
- Every risk change is traceable to factor objects.
- Factor-level reasoning shown in UI.

### Reliability
- If AI is unavailable, deterministic engine still works.
- If recompute fails, persisted latest scores can be returned.

### Real-time responsiveness
- Recompute scheduler triggers updates when profile/vitals/questionnaire/mitigations change.

## 9) Accuracy Evaluation Framework

Script: `backend/src/tests/predictive_accuracy_pipeline.py`

### Metrics reported
- ROC-AUC
- Accuracy
- Precision
- Recall
- F1-score
- Brier score (calibration quality)

### Threshold optimization

Instead of fixed threshold only, script searches threshold in `[0.20, 0.80]`:
- best threshold for **F1**
- best threshold for **Accuracy**

This gives practical deployment flexibility:
- clinical screening priority -> choose higher recall/F1 threshold
- operational false-positive control -> choose higher accuracy threshold

### Validation stability
- 5-fold stratified CV AUC reported for each model

## 12) Current Limitations (Honest, High-Scoring Answer)

- Labeled disease-specific Indian longitudinal datasets are limited in open public access.
- Current benchmark script uses Pima for diabetes proxy testing.
- Multi-disease calibration is still being expanded with disease-specific labeled cohorts.
- External prevalence evidence is used for calibration context, not as direct supervised labels.

## 15) FAQ-Style Ready Answers

### Q1: Is this pure AI?
No. AI is constrained. Deterministic anchors are primary and always validated.

### Q2: Can AI hallucinate a random score?
No. Anchor checks reject invalid outputs and deterministic fallback is applied.

### Q3: Why not use only Logistic Regression in production?
Because clinical explainability + per-disease rule control + dynamic factor narratives are required in product workflow. Regression is used for benchmarking and calibration strategy.

### Q4: How are risk reductions handled?
Only through persisted mitigation completion records, with capped deduction logic.

### Q5: How do you justify trust?
Deterministic anchors, explainable factors, validated schema, fallback paths, and measurable benchmark metrics.
