## PART A — WHERE YOUR PROJECT ACTUALLY STANDS TODAY

Your repo is **two projects overlapping in one codebase**:

1. **"VaidyaSetu"** — an earlier hackathon prototype: a consumer wellness app + herb-drug interaction checker (Groq LLM risk reports, PHQ-2/GAD-2 mental-health screening, thyroid/PCOS/kidney screening quiz, Google Fit steps, Practo doctor-finder, jsPDF reports).
2. **"MediKiosk"** — the hospital platform described in your architecture doc, which a previous build pass already started migrating toward (it even added `docs/MEDIKIOSK_ARCHITECTURE.md` as the "north star" and disabled the old `/api/ai` risk-report route in `server.js` with a comment citing §15).

The migration was **started but not finished**. Some parts are genuinely already well-built and match the architecture closely; other parts are 100% legacy VaidyaSetu and don't belong; and the most important structural piece — **Encounter as the central object (§61)** — was never actually built, so a lot of clinical data still hangs off one giant `IntakeSession` document instead of a normalized `Encounter` graph.

### A.2 — What's structurally broken and must be rebuilt (not cosmetic — this is the core fix)

1. **No `Encounter` entity exists.** §61 is explicit: *"Do not connect clinical data randomly to Patient... route it through Encounter."* Instead everything — vitals, documents, lab orders, SOAP note, consent, access log, diagnoses, red flags, ABDM sync, voice notes — is crammed into one 400-line `IntakeSession` Mongoose schema. This is the single biggest gap. It works for a single OPD visit but cannot support §31–§37 (follow-up encounters), §38 (referrals), or a real longitudinal timeline (§40), because there is no clean parent/child relationship between a patient's *encounters* over time.
2. **No `Patient` / `FamilyMember` model.** `UserProfile.js` is one collection for every role (patient, doctor, reception, admin, lab) and has no concept of a mobile account managing multiple beneficiaries (§2). There is no way today for "Rajesh" to register his mother as a separate health identity under his mobile number.
3. **No `Consent` model.** Consent is captured only as a small embedded object inside `IntakeSession.consent` (4 booleans). §46–§48 requires granular, traceable, per-purpose, revocable consent records with their own ID, method, language, and status — visible on a "My Consent" screen. This does not exist.
4. **No `AuditLog` model.** There's an `accessLog` array embedded per `IntakeSession`, which cannot answer "show me everything Dr. Sharma accessed today" — audit must be its own collection, indexed by actor, not nested per-document.
5. **No `Referral` model or routes.** §38 (referral, same-hospital or cross-hospital) is entirely unimplemented — no model, no route, no UI.
6. **No `FollowUp` model or follow-up queue.** §31–§37 (the "Continuity Engine," which your architecture doc calls the headline differentiator) is only partially represented as flags (`isReturningPatient`, `changesSinceLastVisit`) inside `IntakeSession`. There is no actual follow-up entity, no follow-up time-window assignment, no "Linked Care Task" for multiple pending tests, no second queue.
7. **No `Notification` model/engine.** `reminderService.js` exists but is wired to the old medication-reminder feature, not to the §56 notification set (SMS/WhatsApp/push/kiosk printout/voice for queue status, report-ready, follow-up slot).
8. **No `ABHAIdentity` model.** `abhaId` is a bare string field on `UserProfile`/`IntakeSession`. §2's requirement — treat ABHA creation/linking as an ABDM-governed flow with its own state — has no home to live in.
9. **No `Appointment`/`Queue` as real entities.** Queue state is scattered as fields on `IntakeSession.queueStatus` plus config on `Department`/`Kiosk`. There is no queryable "live queue" collection that the Live Queue screen (§19) or doctor dashboard (§22) can subscribe to cleanly.
10. **Auth is three different half-built systems at once.** `frontend/package.json` has both `@clerk/clerk-react` and `@react-oauth/google` installed; `frontend/src/auth/clerkAdapter.jsx` exists but `App.jsx` wires up Google OAuth directly; the backend has its own `authRoutes.js` + `authMiddleware.js` (JWT). None of these match §2's actual requirement: **mobile number → OTP → identity resolution**, with a **separate, professional-verified identity path for doctors** (§21). This needs to be consolidated into one intentional auth design, not patched further.
11. **`UserProfile.js` is 90% off-architecture.** It carries the entire old wellness-app screening quiz: thyroid, PCOS/women's health, PHQ-2/GAD-2 mental health screen, kidney/liver screening, waist circumference, "saved doctors" with Practo integration, `dataQualityScore`. None of this is in your architecture (§4's Health Profile is basic info + medical info + AYUSH fields, not a diagnostic screening instrument). This must be stripped down and replaced with the real Health Profile shape from §4.

## PART B — THE NORMALIZED DATA MODEL YOU'RE BUILDING TOWARD

This replaces the current `UserProfile` + giant `IntakeSession` design. Give your agent this exact shape as the Phase 1 target. Names match §59's 25-entity list plus `Symptom` and `Appointment` where they clarify things.

```
User                 — login identity only: mobile OR staff credentials, role, hashed OTP/password ref
Patient              — 1:1 with a health identity (self or a family beneficiary)
FamilyMember         — links a Patient record to the User "head of account" + relation
ABHAIdentity         — abhaId, linkStatus, linkedAt, consentArtifactRef (ABDM-governed, not editable locally)
Consent              — consentId, patientId, purpose (enum), dataScope, recipient, method, language, status, grantedAt, revokedAt
Hospital             — (already built — extend, don't replace)
Department           — (already built — extend)
Doctor               — (already built — extend)
Laboratory           — (already built — extend)
Kiosk                — (already built — extend)
Appointment          — patientId, hospitalId, departmentId, doctorId, scheduledFor, type(walk-in/follow-up/booked), status
Queue                — hospitalId, departmentId, doctorId, date, entries:[{patientId, tokenNumber, priority, joinedAt, status}]
Encounter            — THE CENTRAL OBJECT. patientId, hospitalId, departmentId, doctorId, kioskId, type(opd/followup/emergency), status, openedAt, closedAt
Symptom              — encounterId, captureMode(voice/text/touch/bodymap), rawInput, structuredComplaint, bodyRegion
History              — encounterId, mode(modern/ayush), sections:{...per §12/§13}, sourceTags per field
Vital                — encounterId (nullable → also standalone home-logged), values, source(patient/kiosk-device/staff), capturedAt
Medication           — patientId (long-lived, not per-encounter), name, system, status(current/previous/stopped/needs_confirmation), sourceDocId
Prescription         — encounterId, doctorId, items:[MedicationItem], signedAt
Document             — patientId, encounterId (nullable), type, originalFileUrl, uploadedAt, verificationStatus
OCRExtraction        — documentId, rawOcrText, extractedFields:[{field,value,confidence}], languageDetected
InvestigationOrder   — encounterId, doctorId, testName, priority, status, qrPayload
LabSample            — investigationOrderId, collectedAt, collectedBy, sampleId, status
LabResult            — labSampleId, parameters:[{name,value,unit,referenceRange,flag}], verifiedBy, verifiedAt, originalValuePreserved:true
Referral             — encounterId, fromDoctorId, toHospitalId/toDepartmentId/toDoctorId, reason, priority, status
FollowUp             — originEncounterId, reason(lab_result/imaging/review/referral_return), linkedOrderIds:[], status, scheduledWindow, newEncounterId(once created)
Notification          — recipientId, channel(sms/whatsapp/push/kiosk_print/voice), template, payload, sentAt, status
AuditLog             — actorId, actorRole, action, targetType, targetId, patientId, reason, at
AIEvent              — encounterId, service(asr/ocr/historyAI/summaryAI/riskEngine/routing/queuePrediction), input, output, confidence, reviewedByDoctor
```

**Migration note for the agent:** `IntakeSession` becomes `Encounter` plus five child collections (`Document`, `InvestigationOrder`→`LabSample`→`LabResult`, `Vital`, `History`, `Prescription`). Write a one-time migration script (`scripts/migrate_intakesession_to_encounter.js`) that reads every existing `IntakeSession` and fans it out into the new collections, rather than hand-deleting real data — do this even in a demo/hackathon codebase so old QA data isn't lost.

### Phase 2 — Identity, Family Accounts, Consent & Access Control
**Goal:** Implement §2 (mobile+OTP identity, family beneficiaries), §21 (separate doctor identity), and the skeleton of §46–§49 (consent + RBAC).

1. Pick and implement ONE patient auth path: `POST /api/auth/otp/request {mobile}` → SMS OTP (stub provider in dev) → `POST /api/auth/otp/verify {mobile, otp}` → issues session token + returns list of `FamilyMember` profiles linked to that mobile, or "no profiles yet" → new-patient flow.
2. Build `POST /api/patients/family-member` to add a beneficiary (self/father/mother/child/other) — each gets its own `Patient` document and its own `Consent` scope; never share a single `Patient` record across people.
3. Doctor/lab/admin auth stays credential-based (not OTP) — `authRoutes.js` keeps a separate `/api/auth/staff/login`, validated against `Doctor.account`/staff records, not against the patient OTP flow. Wire `roleGuard.js` middleware to check role + (later, in Phase 11) purpose-based scope, not just role.
4. Implement `Consent` CRUD: `POST /api/consent/grant`, `POST /api/consent/revoke`, `GET /api/consent/my` (patient-facing "My Consent" list, §48). Every grant call must populate all §47 fields (purpose, data scope, recipient, method, language, timestamp).
5. Wire `components/kiosk/ConsentScreen.jsx` to call the new endpoints per-purpose (clinical history, document scanning, doctor sharing, lab sharing, ABDM exchange, optional secondary uses) instead of one blanket checkbox.
6. Stub `ABHAIdentity`: `POST /api/abha/link-request` just records intent + status `pending_abdm_flow` — do not fabricate ABHA numbers locally; this is explicitly forbidden by §2's "important correction."

**Acceptance check:** a fresh mobile number can OTP-login, add 2 family members, each with distinct `Patient._id`; consent list correctly shows/hides recipients after grant/revoke; a doctor cannot log in through the OTP endpoint and vice versa.

### Phase 4 — Document Intelligence Pipeline
**Goal:** Formalize §7/§8 — OCR pipeline with `Document` + `OCRExtraction` as real entities, source-linked to the medical timeline.

Rebuild the OCR flow (`ocrRoutes.js`, `visionOcr.js`, `groqVision.js`, `image.js`) to write a `Document` row on upload, then an `OCRExtraction` row per processed page, following the exact pipeline order in §7: quality check → pre-processing → OCR → language detection → medical entity extraction → validation → classification → date extraction → timeline insert.

2. Symptom capture (§10): implement all four input modes (`components/kiosk/SymptomIconPicker.jsx`, `BodyMapSvg.jsx`, voice, free text) writing to one shared `Symptom.structuredComplaint` shape — no mode should produce a differently-shaped record.
3. Generalize `adaptiveSocratesService.js` beyond pain-only complaints into the real §11 engine: input = patient profile + prior `History` + current `Symptom` + `Medication` + prior `Document`s; output = only the missing relevant questions. Keep the "known fields aren't re-asked" behavior it already has.
4. Implement Mode 1 / Mode 2 switch (§12/§13) driven by `Department.intakeConfig.clinicalMode` (already exists on your `Department` model — just make the frontend intake screen actually branch on it). Mode 2's exact question set must read from a per-hospital configurable list, not a hard-coded array.
5. Build the Clinical Knowledge ontology layer (§43) as a static, versioned config (`backend/src/data/clinicalOntology.js`): complaint → required attributes → red-flag triggers. The LLM only fills in natural-language understanding against this structure; it must never invent new required questions.
6. Vitals capture (§14): patient-entered (home, with timestamp+source) vs kiosk-peripheral-captured (auto, no manual typing) — two distinct `Vital.source` values.
7. Red-flag engine (§15/§16): `utils/emergencyScorer.js` becomes a pure function over `Symptom`+`Vital`+`History` → `normal | potential_emergency`; a positive hit always routes to human triage, never an autonomous diagnosis claim. **Acceptance check:** the same knee-pain scenario produces the same `Symptom.structuredComplaint` shape regardless of which of the 4 input modes was used; switching a department's `clinicalMode` from modern to AYUSH changes the question flow live; a red-flag hit always creates a triage task, never a standalone "diagnosis."

### Phase 6 — Queue, Department Routing & Token Engine
**Goal:** Implement §17–§20 with real `Queue`/`Appointment` entities instead of scattered status fields.

1. Department routing (§17): `POST /api/routing/suggest` takes complaint+history+vitals+records → suggested department, explicitly labeled "AI-assisted routing," never framed as diagnosis.
2. Live `Queue` collection per hospital+department+date; `Queue.entries` updated on token issue/consult-start/consult-end. ETA calculation (§18) = patients ahead + doctor's rolling consultation speed (already tracked on `Doctor.consultationStats`) + priority cases + follow-up capacity — always output as a **range**, never false-precision seconds.
3. `pages/QueueDisplay.jsx` and the patient-facing live queue screen consume this via polling or SSE, matching the §19 layout (token, doctor, room, currently-serving, patients ahead, ETA range, status).
4. Token document (§20): render + printable + QR, generated from `qrService.js` at `Encounter` open, containing token/department/doctor/room/patients-ahead/ETA/QR — verify no clinical data is embedded in the QR payload (matches the existing "no clinical data" comment already in your old `IntakeSession.qrPayload`).

**Acceptance check:** ETA always renders as a range string; a completed consultation updates the doctor's rolling average and the next patient's ETA recalculates; scanning the token QR resolves to the correct `Encounter` with zero clinical fields exposed in the QR payload itself.

### Phase 7 — Doctor System
**Goal:** Implement §21–§26 fully: dashboard, 30-second summary, consultation workspace, evidence display.

2. 30-second summary view (§24): current complaint, red flags, new information, known conditions, current medicines, latest vitals, recent investigations — computed server-side from the current `Encounter` + prior `Encounter`s for that `Patient`, not hand-assembled per screen.

### Phase 9 — Continuity Engine: Follow-up & Referral
**Goal:** Implement §31–§38, the feature your architecture doc calls the headline differentiator (§70.5). This is the payoff of doing Phase 1's `Encounter` model correctly.

1. On `LabResult.verified = true`, a background job checks whether the parent `InvestigationOrder`'s encounter is flagged `doctorReviewRequired` → auto-creates a `FollowUp` document (§31) referencing the origin encounter; **never require the patient to re-register from scratch.**
2. Second logical `Queue` type = `followup` (§32), separate from normal OPD, assigned via time windows (§34) computed from report completion + doctor availability + priority + existing queue + hospital capacity — not a first-come free-for-all.
3. Next-day review (§35): doctor marks "Review: Next day" during consult → `FollowUp` gets a date + time window + doctor + room + reason, with **no new token and no repeated intake**.
4. Linked Care Task (§36): when a doctor orders multiple tests, the `FollowUp` waits in a `waiting_for_results` state referencing all `InvestigationOrder` ids, and only becomes schedulable once all linked orders are `verified`.
5. Referral (§38): `Referral` model supporting same-hospital (department→doctor→reason→priority) and cross-hospital (hospital→department→reason→note→QR) paths; receiving side can fetch referral details subject to the same consent/authorization rules from Phase 2.
6. Update the Medical Timeline (Phase 4) to thread `FollowUp` and `Referral` events alongside visits/labs/documents.

**Acceptance check:** completing a lab result for a flagged encounter auto-produces a `FollowUp` with no manual step; a patient with 3 pending tests only gets a follow-up slot once the 3rd result is verified; a same-hospital referral correctly restricts visibility to the receiving department until authorized.
